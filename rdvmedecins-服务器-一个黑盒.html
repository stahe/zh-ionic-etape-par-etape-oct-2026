    8. RdvMedecins 服务器，一个黑盒

    示例 22 至 25 以及随后的案例研究都与一个服务器交互：[RdvMedecins] 应用程序的 JSON 服务器。这是 [NestJS] 服务器，用于 [React]、[Vue.js]、[Angular] 和 [Flutter] 课程：即 [NestJS] 课程的服务器，其控制器不再生成 HTML 页面，而是生成 JSON 响应。这些讲义的读者已经熟悉本章内容，它在此几乎原样重现；他们只需查阅身份验证一节，其中解释了对于安装在手机上的 [Ionic] 应用程序有哪些变化。

    在本课程中，这个服务器是一个黑盒：你不需要知道它是如何编写的。重要的只是它的 API——也就是它接受的 HTTP 请求列表以及它返回的响应。这是客户端开发人员的典型处境：API 是一份契约，服务器团队可以在该契约背后随意更改任何东西。为好奇的读者提供了它的源代码（[rdvmedecins-nestjs-json] 文件夹），并附有大量注释。

    本章说明如何安装服务器，描述它的 API，并使用 [curl] 查询它。

    8.1. RdvMedecins 应用程序

    该应用程序管理医疗诊所的预约。它有三种角色：

    角色
    对象
    可以做什么
    [ADMIN]
    管理员（[admin]）
    为所有患者安排和取消预约；管理医生和客户
    [DOCTOR]
    医生（[pelissier]、[tatou]、[dupont]）
    为所有患者安排和取消预约；在日程中查看所有姓名
    [USER]
    患者（[martin]、[durand]、[bistrou]、[german]）
    为自己预约；取消自己的预约；管理自己的账户。在日程中，他们看不到其他患者的姓名

    演示账户使用其登录名作为密码。管理规则由服务器验证，与客户端无关：

    • 不得在过去的时间预约；
    • 每位患者只能有一个未来的预约；
    • 同一时间段在同一天只能被预约一次；
    • 两位医生（或两位客户）不能有相同的姓和名；一个登录名只属于一个账户；
    • 已有预约安排的医生不能被删除；
    • 已被他人在此期间修改的记录不能被覆盖（乐观锁）；
    • 患者永远不会被分配到另一位患者的姓名。

    8.3. 响应格式

    所有路由都以 [/api] 开头。成功的请求会收到 2xx 状态码，并在响应体中以 JSON 格式返回所请求的数据。被拒绝的请求会收到 4xx 或 5xx 状态码，并在响应体中以相同的格式返回数据：

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "key": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "fields": { "lastName": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode]：HTTP 代码，在响应体中重复出现；
    • [key]：消息的翻译键。服务器从不返回要显示的文本：它不知道用户的语言。由客户端使用它的字典来翻译该键（见示例 21）；
    • [params] （可选）：消息参数（“At least {{min}} characters”、“Please try again in {{minutes}} minute(s)”）；
    • [fields] （可选）：对于被拒绝的表单，每个字段的错误。

    8.4. 身份验证

    客户端使用 [POST /api/auth/login] 进行身份验证，提交用户名、密码和验证码答案。作为回应，服务器在其响应的 [Set-Cookie] 头中发送一个包含已签名 JWT 令牌的 Cookie：

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; Expires=Tue, 06 Oct 2026 14:12:15 GMT; HttpOnly; SameSite=Strict

    此后，客户端必须在每个请求的 [Cookie] 头中带上这个 Cookie，这些请求发往 [/api]：服务器就是这样知道是谁在发出请求的。

    这个服务器是为 Web 客户端设计的，它的设计选择由 Web 浏览器特有的风险所驱动：

    • [HttpOnly]：页面上的 [JavaScript] 代码无法读取这个 Cookie。因此，注入页面的恶意脚本无法窃取令牌。对客户端的影响：它无法自行判断自己是否已登录。它需要询问服务器（[GET /api/auth/me]）；
    • [Path=/api]：该 Cookie 只会包含在发往 API 的请求中；
    • [SameSite=Strict]：浏览器只会在发往本站页面的请求中包含该 Cookie。另一个站点上的恶意页面无法让浏览器以用户的名义执行操作（即所谓的 CSRF 攻击）；
    • [Max-Age=7200]：它在两小时后过期，与令牌过期的时间相同。

    针对 CSRF 攻击的第二道防线：服务器会拒绝（415）任何请求体不是 JSON 的 POST 请求。另一个站点上被入侵的 HTML 表单无法发送 JSON。

    8.4.1. 移动客户端有哪些变化

    [Ionic] 应用是一个由“WebView”（来自 [Chrome] 的浏览器引擎，位于 [Android] 上）在手机上运行的 Web 应用：它遵循与浏览器相同的规则吗？在本课程中，我们需要区分它的两种运行方式。

    在电脑的浏览器中，开发期间（[ng serve]）。应用程序由 [Angular] 开发服务器（http://localhost:8100）提供；JSON 服务器位于另一个端口（8080）。这是两个不同的源，浏览器会应用两条有问题的规则：除非服务器授权（即“CORS”机制，我们的服务器不支持），否则它不会接受来自不同源的响应；并且它不会在“来自另一个站点”的请求中包含 [SameSite=Strict] Cookie。解决办法与 [React] 和 [Vue.js] 课程中相同：使用代理。开发服务器会把所有地址以 [/api] 开头的请求转发给 JSON 服务器（文件 [proxy.conf.json]，见示例 22）。从浏览器的角度看，应用程序和 API 具有相同的源：浏览器会存储该 Cookie 并把它发回，而应用程序代码无需做任何事情。

    在手机上 （[Android]、[Capacitor]）。页面由 [Capacitor] 自身从地址 https://localhost 提供；JSON 服务器在电脑上，地址类似 http://10.0.2.2:8080（见示例 22）。同样，这里也有两个源。项目启用了 [CapacitorHttp] 插件，来自 [Capacitor] （文件 [capacitor.config.ts]）：应用程序的 HTTP 请求不再由 WebView 发送，而是由 [Android] 的原生代码发送。其影响如下：

    • 不再有 CORS 检查：这项检查是浏览器的规则，而原生代码不是浏览器（[curl] 也不是）；
    • 收到的 Cookie 由 [Android] 存储（它的 Cookie 管理器，与 WebView 的相同），并在之后发往同一服务器的请求中自动带回。它们保留在设备上：关闭再重新打开应用后，你仍然处于登录状态；
    • [HttpOnly] 和 [SameSite] 属性不会造成任何问题：应用程序代码从不读取该 Cookie（它通过 [GET /api/auth/me] 询问谁已登录），而且请求也不是由“来自另一个站点”的页面发出的。

    这与 [Flutter] 课程有一个重要区别：[Flutter] 应用没有浏览器，必须编写自己的 HTTP 客户端，在响应中读取 [Set-Cookie] 头，并在请求中写入 [Cookie] 头。而使用 [Ionic] 时，无论是在浏览器中还是在手机上，Cookie 都会被自动传递，无需一行代码。而服务器这边无需做任何改动：它看到的只是普通的 HTTP 请求，其中包含它设置的 Cookie。

    8.6. 使用 curl 查询 API

    服务器上的 [curl] 文件夹包含本章各请求的 JSON 请求体，每个请求一个文件。例如 [curl/login-admin.json]：

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    这些命令在打开到 [rdvmedecins-nestjs-json] 目录的控制台中输入，服务器以验证码测试模式（[CAPTCHA_TEST=test]）运行，数据库刚刚（重新）初始化过。[curl] 的一些选项：

    • [-i]：同时显示响应头；[-s]：不显示进度条；
    • [--json @file]：以 POST 发送文件的内容，并带有头 [Content-Type: application/json] （[curl] 7.82 及更高版本；对于较旧的版本，使用 [-H "Content-Type: application/json" -d @file]）；
    • [-X PUT]、[-X DELETE]：HTTP 方法；
    • [-c cookies.txt]：把收到的 Cookie 保存到这个文件中；[-b cookies.txt]：把它们发送回去。[curl] 就是这样在各条命令之间“保持登录”的，就像浏览器那样。

    在 [PowerShell] 下，必须输入 [curl.exe] 而不是 [curl] （后者指的是另一个命令）。以下输出来自一次真实的会话（2026 年 10 月 6 日，预约安排在 2030 年 1 月，因此它们仍然在未来）。篇幅较长的 JSON 响应已为本文档做了格式化（每个对象一行），JWT 令牌和验证码图片已被截断（“...”），并且已删除头 [Date]、[ETag]、[Connection] 和 [Keep-Alive] 。
